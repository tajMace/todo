# todo — v2 spec: feature layer on the Go core

No rewrite. No new language. Same discipline as v1: hard time box, vertical
slices, backward-compatible with existing `~/.todo.json` files created by v1.

## Scope

**In:** `project`, `priority`, `tags`, `notes`
**Deferred to v3+:** recurring tasks, time tracking, NLP due dates,
context-aware views, SQLite backend

### Why these four and not others

Options considered and cut, so they don't creep back in mid-build:

| Considered | Verdict | Why cut |
|---|---|---|
| `project` | **In** | Your own v1 example data (`COMP1531 auth tests`) is already implicitly project-tagged. Cheap field, high daily value. |
| `priority` | **In** | One enum field, one sort key. Near-zero cost, real value for `list` ordering. |
| `tags` | **In** | Freeform array, orthogonal to `project` (project = one bucket, tags = cross-cutting labels like `urgent`, `blocked`). Cheap. |
| `notes` | **In** | Single optional string for context that doesn't fit in the title. No parsing, no new commands — just a field. |
| `pinned` / starred | Cut | Marginal over `priority: high` — would be a second, competing "this matters" signal. |
| Subtasks / checklists | Cut | Real feature, not a field — needs its own data model and commands. v3 candidate if wanted. |
| Color-coded tags | Cut | Presentation concern, belongs in v1.1 TUI styling, not the data layer. |
| `--sort` flag (custom sort order) | Cut | One sensible default sort covers this; a flag is complexity for a rare need. |

## Data shape

```json
{
  "id": 1,
  "text": "Finish COMP1531 auth tests",
  "done": false,
  "due": "2026-07-28",
  "project": "COMP1531",
  "priority": "high",
  "tags": ["uni", "urgent"],
  "notes": ""
}
```

- `project` — optional string, freeform, no separate project-management step or registry
- `priority` — optional enum: `low | med | high`; absent = no priority (sorts last, same as v1 undated behavior)
- `tags` — optional `[]string`, freeform, normalized to lowercase + trimmed on write
- `notes` — optional string, freeform, no length cap for v2
- **Backward compatibility:** any v1 JSON file with entries missing these fields must load cleanly — missing `project`/`priority`/`notes` → `""`/unset, missing `tags` → `[]`

## CLI changes

```
todo add "title" [--due YYYY-MM-DD] [--project NAME] [--priority low|med|high] [--tag TAG]... [--notes "text"]
todo list [--project NAME] [--tag TAG] [--priority low|med|high]
todo done <id>      # unchanged
todo rm <id>        # unchanged
```

- `--tag` is repeatable (`--tag uni --tag urgent`)
- `list` filters are AND'd together when combined (e.g. `--project COMP1531 --priority high`)
- No filter flags = current v1 behavior (all open tasks)

## Sort order for `list`

1. Overdue (due date < today), most overdue first
2. Priority: `high` → `med` → `low` → unset
3. Due date ascending, within same priority tier
4. Undated, no priority — last, in id order

This replaces v1's "due date, undated last" with a priority-aware version;
v1's behavior is the special case where no task has a priority set.

## Design note (carried over from v1)

Same rule as before: `add` / `list` / `done` / `rm` stay plain functions, no
direct stdout/`os.Exit` inside them. New fields and filters flow through the
same function signatures (extra optional params or an options struct) —
`main.go` and, later, the TUI both call the same core.

## Tickets

Vertical slices, in build order. Each should be shippable/testable on its own
before moving to the next.

### V2-01 — Extend data model + backward-compat load
**Description:** Add `project`, `priority`, `tags`, `notes` to the task
struct. Update JSON (un)marshaling so old v1 files load without error and new
fields default sensibly.
**Acceptance criteria:**
- [ ] Struct updated with new optional fields
- [ ] Loading an existing v1-format `.todo.json` (no new fields present) succeeds, new fields default to zero values
- [ ] Saving round-trips correctly (load → save → load produces identical data)
- [ ] Unit test with a fixture v1 JSON file

### V2-02 — Priority validation + type
**Description:** Introduce a `Priority` type/enum (`low`/`med`/`high`) with
validation, reused by both `add` and `list --priority`.
**Acceptance criteria:**
- [ ] Invalid priority string (e.g. `--priority urgent`) errors clearly, doesn't write bad data
- [ ] Valid values accepted case-insensitively (`HIGH` == `high`)
- [ ] Unit tests for valid/invalid inputs

### V2-03 — `add` accepts new flags
**Description:** Wire `--project`, `--priority`, `--tag` (repeatable),
`--notes` into `todo add`.
**Acceptance criteria:**
- [ ] All four flags work individually and combined
- [ ] Tags normalized (lowercase, trimmed, de-duplicated) on write
- [ ] `add` with none of the new flags behaves exactly as v1 (regression check)
- [ ] Tests cover each flag + combination

### V2-04 — `list` filtering
**Description:** Add `--project`, `--tag`, `--priority` filters to `todo
list`, AND'd when combined.
**Acceptance criteria:**
- [ ] Each filter works standalone
- [ ] Combined filters narrow correctly (AND, not OR)
- [ ] No filters = current v1 output (regression check)
- [ ] Tests for empty-result cases (filter matches nothing)

### V2-05 — Priority-aware sort order
**Description:** Update `list`'s sort to: overdue → priority → due date →
undated, per spec above.
**Acceptance criteria:**
- [ ] Tasks with no priority sort identically to v1 (regression check)
- [ ] Mixed priority + due date fixtures sort in the documented order
- [ ] Overdue tasks always surface first regardless of priority
- [ ] Test fixture covering all four tiers at once

### V2-06 — Display formatting
**Description:** Update `list` output to show project, priority, and tags
inline without cluttering plain undecorated tasks.
**Acceptance criteria:**
- [ ] Task with no new fields set prints identically to v1 (regression check)
- [ ] Task with all fields set prints readably (no field collides visually)
- [ ] `notes` shown only in a future `todo show <id>` — not cluttering `list` (see V2-08, optional)

### V2-07 — README + CHANGELOG update
**Description:** Document new flags, data shape change, and migration note
(old files just work, no migration step needed).
**Acceptance criteria:**
- [ ] README examples updated for all new flags
- [ ] Explicit "upgrading from v1" note confirming no manual migration needed

### V2-08 — (Stretch, optional) `todo show <id>`
**Description:** Only if time remains after V2-01–07. A detail view for a
single task, primarily to surface `notes` without cluttering `list`.
**Acceptance criteria:**
- [ ] Prints all fields for one task by id
- [ ] Errors cleanly on unknown id
**Note:** cut without guilt if the time box runs out — it's explicitly
stretch, not core.
