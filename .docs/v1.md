# todo — project plan

A small CLI todo tool, built to actually ship, in Go.

## Why this scope

The goal isn't the "best" todo tool — it's finishing a real, working thing in a
short, defined window. Every decision below optimizes for that: boring tech,
small surface area, vertical slices, hard stop on scope creep.

## v1 — CLI, no UI

Just the core logic and commands. Everything here should be provably correct
and testable in a couple minutes per command.

**Commands**
- `todo add "title" [--due YYYY-MM-DD]`
- `todo list`
- `todo done <id>`
- `todo rm <id>`

**Data shape**
```json
{ "id": 1, "text": "Finish COMP1531 auth tests", "done": false, "due": "2026-07-28" }
```
- `due` is optional, plain `YYYY-MM-DD` string — no natural language parsing, no time-of-day.
- Stored as a single JSON file, e.g. `~/.todo.json`.
- Single user, single terminal at a time — no concurrency handling needed.

**v1 checklist**
- [ ] `todo add` works, with and without `--due`
- [ ] `todo list` shows open tasks, sorted by due date (undated last)
- [ ] `todo done <id>` marks complete
- [ ] `todo rm <id>` deletes
- [ ] Runs as a global `todo` command (not `go run` / `node index.js`)
- [ ] Doesn't crash if the JSON file doesn't exist yet
- [ ] Short README

**Design note:** keep `add` / `list` / `done` / `rm` as plain functions that
take and return data — no direct stdout printing or `os.Exit` calls buried
inside them. Let `main.go` be a thin layer that calls these functions and
formats output. This is what makes v1.1 easy: the TUI just calls the same
functions instead of duplicating logic.

## v1.1 — TUI

Once v1 is done, shipped, and used for a bit — wrap it in a real terminal UI.

- **Framework:** [Bubble Tea](https://github.com/charmbracelet/bubbletea) (Elm Architecture: Model / Update / View)
- **Styling:** Lip Gloss (borders, colors, layout)
- **Components:** Bubbles (text input, list, etc.)
- List view with cursor navigation (vim-style hjkl + arrow keys)
- Input for `add`
- Calls the same v1 functions under the hood — no logic duplication

## Explicitly out of scope (for now)

Ideas parked for later, not to be pulled into v1 or v1.1:
- Priorities, tags, projects/course grouping
- Time-of-day / natural language due dates ("tomorrow", "next friday")
- Recurring tasks
- per repo .todo
- Context-aware views (auto-filter by cwd/tmux session)
- Time-boxing / time tracking
- SQLite or any DB backend
- Rust rewrite (deliberate v2, once v1 logic is proven and stable)

## Tech decisions and why

| Decision | Choice | Why |
|---|---|---|
| Language | Go | Fast to ship, simple tooling, no fighting the compiler mid-project |
| Storage | Flat JSON file | Zero setup, sufficient for single-user local use |
| Interface (v1) | Argument-based CLI | No interactive complexity until logic is proven |
| Interface (v1.1) | Bubble Tea TUI | Best-in-class Go TUI stack, Elm architecture keeps state clean |
| Rust | Deferred | Learn it as a rewrite of known-working logic, not while also designing the project |

## Pacing

- Hard time box, not a hard feature box (e.g. 3 evenings, ~90 min each)
- Build vertically: `add` working end-to-end before touching `list`
- When the checklist is done, ship it — tag `v0.1.0`, write the README, stop
- Resist "just one more thing" — anything not on the checklist is v2
